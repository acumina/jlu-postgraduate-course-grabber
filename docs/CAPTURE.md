# 抓包实战指南（CAPTURE）

这份文档教你用 Chrome DevTools 手工抓出真实的选课请求，导出 HAR，并把它翻译成插件能用的配置。
适用前提：你已经在 `chrome://extensions` 里加载了本扩展，并且能在浏览器里正常登录、正常选课。

> 本文里的控件名按当前实现写：页面内面板有五个页签——**抓包 / 目标 / 余量 / 日志 / 设置**，工具栏弹窗有「启动抢课」「停止」「检测登录态」「我刚登录了」「打开登录页」「小窗工作台」「新标签页打开」「把当前站点加入白名单」等按钮。如果你的界面与此不符，说明版本不同，以实际界面为准。

## 一、打开 DevTools 的网络面板

1. 在选课页面按 `F12`（或 `Ctrl+Shift+I`）打开 DevTools，切到 **Network** 标签。
2. 勾选 **Preserve log**（保留日志）。选课提交后页面经常会跳转或重载，不勾这一项，请求记录会在跳转时被清空，你就白抓一次。
3. 建议把过滤切到 **Fetch/XHR**：选课请求基本都是 AJAX，这样能过滤掉图片、CSS、埋点等噪音。
4. 如果请求太多，可以在过滤框里试关键词：`elect`、`xk`、`save`、`submit`、`select`、`jx`（不同学校命名不同，按你页面上的实际请求试）。

> 省事的做法：扩展面板的**「抓包」页**已经在记录页面自己发出的 `fetch` / `XMLHttpRequest`（页面加载后自动开始，最近 40 条会留存在本地）。很多时候你根本不用开 DevTools——直接看那一页、点「详情」就够了。DevTools 更适合要求精确控制（只看某一次操作、导出 HAR、看完整响应）的场合。

## 二、清空日志，然后只做一次操作

1. 点 Network 面板左上角的 🚫 **清空**按钮（Clear），把之前的记录清掉。
2. 在页面上**只做一次**你想复现的动作——比如在某个教学班后面点一次「选课」。
3. 除了这一次点击以外，**不要翻页、不要排序、不要点搜索、不要切换学期标签**。每多一个动作，就多一批请求，你就越难判断哪条才是真正的提交请求。

为什么强调「只操作一次、动作越少越好」：

- 请求列表越短，候选越少，越不容易认错。
- 插件是**用你抓到的这条请求当模板**的。模板必须只包含「提交选课」这一个语义；如果你顺手点了别的按钮，很容易把查询类的请求当成提交请求存下来。
- 后续做「差分」时，你需要的是「同一个动作、不同课程」两条请求，噪音越少对比越干净。

> 想先练手：仓库自带一个零依赖的假教务系统（`node mock/server.mjs`，打开 `http://127.0.0.1:8787`），里面的抓包/模板/余量/验证码流程和真系统一致，用来把本文这套操作练熟最安全——练完再去抓真系统。

## 三、导出 HAR

两种方式，按需要选：

- **单条请求**：在请求上右键 → **Copy** → **Copy as cURL**（或 Copy as fetch）。适合马上要对比、要拿去用的时候。
- **整批导出**：在请求列表空白处右键 → **Save all as HAR with content**，保存成例如 `capture.har`。
  - 必须带 **with content**，否则导出文件里没有请求体和响应体，插件和转换脚本都没法用。
  - 不想带上无关请求时，可以在导出前先把不相关的域名过滤掉，或者干脆重新清空后再只抓一次。

生成的 HAR 里包含请求头（**含你的 Cookie**），请当作敏感文件对待，不要随手分享。

### HAR 文件里有什么（便于你和转换工具对照）

HAR 是通用 JSON 格式（HAR 1.2），关键结构大致如下：

```json
{
  "log": {
    "entries": [
      {
        "request": {
          "method": "POST",
          "url": "https://jwxt.example.edu.cn/xk/save",
          "headers": [{ "name": "Content-Type", "value": "application/x-www-form-urlencoded" }],
          "postData": { "mimeType": "application/x-www-form-urlencoded", "text": "jxb_id=2024-0001&xnm=2024" }
        },
        "response": {
          "status": 200,
          "content": { "mimeType": "application/json", "text": "{\"msg\":\"选课成功\"}" }
        }
      }
    ]
  }
}
```

- `request.postData.text` 就是你界面上看到的 Payload，**核对 ID 参数主要看这里**。
- `response.content.text` 是响应体。只有导出时选了 **with content** 才有内容，否则是空的——这就是前面强调的原因。
- `tools/har2config.mjs` 读的正是这些字段；拿它生成配置后，请对照真实值逐项确认它猜得对不对。

## 四、这条请求要看哪些字段

挑出那条真正的提交请求后，逐项抄下来：

**1. Request URL 与 Method**

- 完整地址（含 `?` 后面的查询串），以及是 `GET` 还是 `POST`。
- 教务系统一般把「学期、批次」这类上下文放在 URL 查询串或 body 里，两者都要看。

**2. 请求头（Request Headers）**

| 头 | 处理方式 |
| --- | --- |
| `Cookie` | **不要复制**。浏览器会根据当前会话自动带上，手工写进去只会引入过期凭据。 |
| `Content-Type` | 要记下来。`application/x-www-form-urlencoded` → 插件里 `contentType` 填 `form`；`application/json` → 填 `json`；其他（如表单 multipart、自定义）→ 填 `raw` 并自己写头。 |
| `X-Requested-With` | 通常要保留（常见值 `XMLHttpRequest`），后端很可能用它区分 AJAX 与普通请求。 |
| `Referer` / `Origin` | **不要手抄进配置**。它们是浏览器自己管理的头：fetch/XHR 根本不允许手工设置（会被静默忽略），而插件是在选课页面里**同源**发包的，浏览器本来就会自动带上正确的 `Referer`（当前页面地址）和 `Origin`，系统的来源校验照常通过。只有在系统严格校验「必须是指定那个地址」且当前页面地址不是它时要特殊处理：这时用插件的高级字段 `submit.referrer` 指定（**同源才有效，跨源会被浏览器按策略剥掉**，这是浏览器行为，绕不过去）。 |
| CSRF / token 类 | 常见名字：`X-CSRF-TOKEN`、`X-XSRF-TOKEN`、`X-Token`、`_token`（后者常在 body 里）。**能保留就保留**；如果它是页面里一次性下发的，抄死在配置里可能会过期，需要重新抓。 |
| `Authorization` | 若存在，按 token 类同样对待。 |

**3. Payload / Form Data —— 找出「选课 ID」**

这是最关键的一步。你要找的是**唯一标识这节课（这个教学班）**的那个参数，插件里的 `targets[].id` 就是它的值。常见的参数名：

- `jxb_id`（教学班号，最常见）
- `xkkh`、`xkkh_id`（选课课号）
- `kch_id` / `kch`（课程号，注意：这是「课程」级，不是「教学班」级）
- `bjh`、`classId`、`teachingClassId`、`id`、`courseId`
- 中文参数名也常见：「教学班」「选课号」「课序号」「课号」

同时把**每学期固定不变**的参数记下来（例如 `xnm`（学年）、`xqm`（学期码）、`rwlx`、`sj`、`type` 等），它们应当写进 `submit.vars`，而不是当模板变量。

**4. 响应（Response）—— 判断成功与已满**

在 Response 标签里看返回内容（很多教务系统返回 JSON，也有直接返回 HTML 片段的）：

- 成功典型文本：`选课成功`、`操作成功`、`SUCCESS`、`{"code":0,...}`、`状态:1`。
- 已满典型文本：`容量已满`、`人数已满`、`余量为0`、`该教学班已满`。
- 重复：`已选`、`重复选择`、`已经选过`。
- 风控/异常：`验证码`、`滑块`、`verify`；`未登录`、`登录超时`、`session` 过期；`未开放`、`不在选课时间`、`选课已结束`。

把上面这些文案对应到插件 `submit.rules` 的六条规则里（`success` / `full` / `dup` / `captcha` / `logout` / `closed`）。**务必用你实际看到的原文**，默认正则只是常见文案的兜底。

**5. 如果能找到「查余量」的请求**

很多系统在选课页会用一条请求拉课程列表（常带 `remain`、`syrs`、`key` 之类的余量字段）。如果这条请求好复现、参数简单，就在插件里把 `query.enabled` 打开并配置它，这样引擎可以「先查余量、有余量才提交」，请求量小得多；否则就用默认的盲发模式。

## 五、用两条不同课程的请求做「差分」（最实用的技巧）

只凭一条请求，你很难分清哪些参数是「这节课的身份」，哪些只是上下文。做法是抓两条**不同教学班**的提交请求，逐参数对比：

1. 清空 Network，操作一次课程 A 的选课，记下这条请求。
2. 再清空 Network，操作一次课程 B 的选课（换一个教学班，最好是同一门课的不同班，或不同课），记下这条请求。
3. 分别右键 → **Copy as cURL**，粘贴到同一个文本编辑器里，把两条的 body/headers 拆成一行一个参数，上下对齐比较。
4. 结果只会是两类：

| 对比结果 | 结论 |
| --- | --- |
| 两条完全相同的参数 | 上下文参数（学期、批次、token 等），写进 `submit.vars` 或原样保留在 body 里。 |
| 两条不同的参数 | 候选的「选课 ID」。值是 A 的班号和 B 的班号，说明你找对了。 |
| 有多于一个参数不同 | 需要再来一条 C 请求判断：只跟 A 相同的那个是真正的 ID，另一个可能是课程号、批次号或时间戳。 |

5. 判断标准：这个参数的取值应该**能唯一指向你点的那一个教学班**。如果两个不同的班在这个参数上取值一样，它就不是 ID（典型例子：`kch` 课程号——同一门课的所有教学班它都一样）。

小技巧：

- 也可以把两条请求 **Copy as fetch** 后粘贴在一起肉眼 diff；或把两条的 Payload 分栏抄进一张表，逐行打勾/打叉。
- **让扩展替你算**：在面板「抓包」页勾选这两条请求（勾选框在每条请求左上角），点**「对比找出变化的参数字段」**，它会按打分从高到低列出「键相同、值不同」的参数；确认哪个是选课 ID 后点**「这就是选课ID → {{id}}」**，它会以「勾选里最新的那条」为基准设为提交模板并完成替换。也可以先点某条的**「详情」**，在参数表里逐行点「→ {{id}}」或「→ {{kch}}」手工标注。

## 六、把抓到的信息填进插件（三种方式）

1. **面板里点按钮**（推荐）：先手工选一次课（抓包是页面加载后自动开启的，不需要点「开始抓包」），然后在面板的**「抓包」**页里：
   - 找到那条提交请求 → 点**「设为提交模板」**（URL、方法、Content-Type、请求头和 body 会自动填进 `submit`）；
   - 想省掉一条请求就对课表/余量那条点**「设为余量查询模板」**；
   - 参数拿不准就点**「详情」**，或勾选两条不同课程的请求点**「对比找出变化的参数字段」**，再点**「这就是选课ID → {{id}}」**。
   最后切到**「目标」**页，把选课 ID 按 `选课ID,备注` 一行一条粘进导入框，点**「导入上面这些」**。
2. **手工填设置页**：把你抄下来的值分别填进 `submit.url` / `submit.method` / `submit.contentType` / `submit.headers` / `submit.body`（body 里把 ID 的位置写成 `{{id}}`，固定值写成 `submit.vars` 里的键），再配好 `submit.rules` 和 `targets`。余量查询同理填 `query.*`。
3. **`tools/har2config.mjs` 转换**：用导出的 HAR 自动生成一份配置，再人工核对。

```bash
node tools/har2config.mjs capture.har --host jwxt.example.edu.cn --out kx-config.json
```

完整用法是 `node tools/har2config.mjs <capture.har> [--out 文件] [--host 主机] [--pretty]`：它按 `--host` 过滤主机，给请求分类打分（提交 / 查询 / 其它），并用**结构相同的多条请求做差分**找出「键相同、值不同」的选课 ID 字段，模板化成 `{{id}}` 后输出一份与 `src/lib/config.js` 的 `defaults()` 同构的配置。

- 输出内容**就是 `kx_state` 的值本身**，导入方式是 `chrome.storage.local.set({ kx_state: <文件内容> })`，或直接把 JSON 粘到面板设置页的导入框里点「从下面的框导入」；用了 `--pretty` 时记得先删掉多出来的 `_report` 字段。
- 分析报告（候选接口排行、ID 候选、可疑点、必须人工确认的字段）始终打到 stderr。
- 生成的配置里 `enabled` 固定是 `false`，Cookie 也不会被写进去（浏览器自动携带）。
- **自动推断一定会猜错一些东西**（`submit.rules` 仍是通用默认正则、`targets[].label` 多为空、`query.parse` 字段名要靠你确认），请逐项对照真实请求核对后再启用。

## 七、Copy as cURL 的用法与安全提醒

- 用途：快速复现一条请求、把模板信息抄成一行、或在排查时确认「不加 Cookie 时会怎样」。
- 你可以在终端里直接跑，例如（PowerShell 下把 `curl` 换成 `curl.exe`）：

```bash
curl.exe 'https://jwxt.example.edu.cn/xk/save' -X POST ^
  -H 'Content-Type: application/x-www-form-urlencoded' ^
  -H 'X-Requested-With: XMLHttpRequest' ^
  --data-urlencode 'jxb_id=2024-0001' ^
  --data-urlencode 'xnm=2024'
```

- **安全提醒**：Copy as cURL 的字符串里**包含你的 Cookie 和各类 token**。等同于一串账号凭据：
  - 不要发到群里、贴到论坛、提交到 git、放进截图。
  - 不要交给任何「帮你调试」的陌生人或在线工具。
  - 用完就删；如果确实泄漏了，尽快去教务系统改密码 / 重新登录让旧会话失效。

## 八、给学生用户的操作与风控注意事项

- **别把间隔调到 100ms**。这既没有实际收益（教务系统本身几十到几百毫秒就返回了），又几乎必然触发风控。建议 `intervalMs` 不低于 1500–3000ms，`jitterPct` 保持在 25% 左右。
- **别多开大量标签页**。引擎本来就只跑在一个工作标签页里；开一堆标签页既不会更快，还会放大请求量并让页面更难管理。
- **出现验证码就停手**。插件的默认配置会在命中 `captcha` 规则时自动停机——不要绕开它。手动过掉验证码、等风控冷静下来再决定要不要继续。
- **优先做「只监控不提交」**。把 `submitOnHit` 关掉，先让插件提醒你「有余量了」，你自己回页面点一下。这既安全得多，也基本满足「不用一直盯着屏幕」的需求。
- **选课高峰期不要挂机猛刷**。系统崩了大家都选不了，高频请求只会让你的账号更早被盯上。
- **别用别人的账号**。Cookie 会随请求带上，用他人会话操作属于越界行为，也可能违反校规。
- **别把成果变成交易**。不要用这套工具帮别人抢课或收费，风险和争议都远超收益。

## 九、怎么判断自己遇到的是「硬超时」还是「空闲超时」

这决定了 `session.keepAlive.enabled`（心跳保活，默认关闭）该不该打开：

- **硬超时**：从登录成功那一刻起算，满 N 分钟就无条件失效，跟你有没有在操作完全无关。心跳包救不了它——所以默认关闭保活，改成「倒计时提醒你重新登录」。
- **空闲超时**：只要你持续操作（发请求）会话就续期，停手 N 分钟才失效。这种情况打开心跳保活是有意义的。

测法（需要 20 分钟以上，建议在非选课高峰时段做；**先把引擎停掉**，否则插件自己的探测会干扰结论）：

1. 正常登录教务系统，打开一个能正常返回数据的选课/查询页面，确认此时查询是好用的。
2. **完全不要动它**：不点、不刷新、不切学期标签，也不要在别的标签页里操作教务系统。
3. 在第 **5 / 10 / 15 / 19 / 21 分钟**各做一次「普通查询」（例如点一次「查询课程」，或翻一页课程列表），每次都如实记下结果：

| 观察结果 | 结论 |
| --- | --- |
| 某一次开始跳登录页、提示「请重新登录」、或查询返回空/报错 | 真实超时时间落在这之前最后一次正常与这一次失效之间，按最早失效的那次估计。 |
| 5 / 10 / 15 / 19 分钟都正常，21 分钟失效 | 典型的**满 20 分钟硬超时**。 |
| 一路到 25、30 分钟都没掉 | 可能是更长的超时，或者服务器根本不管会话时长；继续按 25 / 30 分钟各测一次。 |

4. 做一组对照实验：**同样 20 分钟，但每隔 3–4 分钟点一次普通查询**。

| 对照组结果 | 结论 |
| --- | --- |
| 一直不掉线 | 是**空闲超时**，操作能续期 → 可以把 `session.keepAlive.enabled` 打开（心跳按 `keepAlive.intervalMs` 节奏发，虽然当前实现实际用的是 `session.probeEveryMs`，见 README）。 |
| 到点照样掉线 | 是**硬超时** → 心跳没有意义，**保持 `keepAlive.enabled = false`**，靠倒计时提醒你重新登录。 |

测出来之后怎么用：

- 把实测时长填进 `session.hardTimeoutMs`（毫秒，例如实测 12 分钟就填 `720000`），把 `session.warnBeforeMs` 设成你来得及重新登录的提前量（默认 180000 = 3 分钟）。填准之后，弹窗「登录态」一行会显示剩余时间，到点前会弹一次桌面通知 + 提示音。
- 如果实测超时明显短于 20 分钟，顺手把 `engine.intervalMs` 调保守一点：登录失效期间引擎会停机等待重新登录，太激进的间隔只会让「停机—重启」更频繁。
- 如果你怀疑自己错过提醒而白白挂了很久，看看日志页有没有「已到达推定硬超时时刻，立即探测登录态」和「登录已掉线」这两类记录——它们说明插件已经在被动等你了。

## 十、启用前的复核清单

抓包得到的模板填进配置后，先按这份清单自查一遍，再打开总开关：

- [ ] `sites` 里填的是抓包所在站点的**主机名**（不要填 `https://` 和路径）。
- [ ] `submit.url` 与抓包里的 Request URL 完全一致（含查询串）。
- [ ] `submit.method` 与真实方法一致（多数是 `POST`）。
- [ ] `submit.contentType` 与真实 `Content-Type` 匹配（`form` / `json` / `raw`）。
